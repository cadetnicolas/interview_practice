# 考点地图：智能体 / 大模型应用开发

**这不是题目池。** 不要从这里抽题，不要按顺序问。题目一律从候选人的简历和 JD 现场生成（见 `../question-design.md`）。

用途只有一个：**他答完之后，查这里——这一答落在哪个考点、什么算过线、该往哪追。**

分组与 `roles/agent-dev.md` 的五个维度对应。

---

## 一、方案与判断

### 该不该用 Agent
**触发**：简历写"用 Agent 解决 XX"，但没说明为什么必须是 Agent
**好回答**：先判断问题是否真的开放——输入是否高度多样、步骤是否需动态决策、失败是否可容忍；如果是确定流程，规则或传统工程更可靠更便宜
**假好**：把 Agent 当万能解；说"大模型能力够强所以能做"
**追问**：① 不用 Agent 的方案是什么，差在哪 → ② 失败一次代价多大 → ③ 哪些环节必须人工确认

### 架构选择：单 Agent vs 多智能体
**触发**：提到"多智能体""编排""工作流"
**好回答**：该用多智能体的条件是子任务可清晰切分且各需不同上下文/工具、需要并行、需要独立视角交叉验证；失败模式是信息交接丢失、职责重叠、错误放大、调试困难、成本翻倍
**假好**：把"多智能体"当高级的同义词；说不出协调成本
**追问**：① 为什么单 Agent + 工具不够 → ② 交接时上下文怎么传 → ③ 出错时你怎么定位是哪一环

### 微调 vs RAG vs prompt
**触发**：提到"微调""训练自己的模型"
**好回答**：prompt 先试；RAG 用于知识需更新/需溯源/知识量大；微调用于固定风格格式、压缩成本（小模型替大模型）、任务模式稳定但 prompt 表达不清；微调不擅长注入新知识且难更新；三者常组合——微调定行为，RAG 供知识
**假好**：遇到问题就说"微调一下"
**追问**：① 为什么不用 RAG → ② 微调后怎么更新知识 → ③ 数据从哪来，多少条

## 二、工程与可靠性

### 工具设计与错误自愈
**触发**：提到"接入 XX 个工具""function calling"
**好回答**：工具描述要能回答"何时该用"；参数语义清晰且数量可控；错误信息要告诉模型"哪里错、怎么改"；工具要幂等、有超时与重试语义；工具过多会显著降低选择准确率，需分层或路由
**假好**：把内部 API 原样暴露成工具；错误只返回"失败"
**追问**：① 模型选错工具怎么发现 → ② 工具返回错误后它能自己纠正吗 → ③ 工具数量到多少会退化

### 上下文工程
**触发**：提到"长文档""多轮对话""记忆"
**好回答**：分层处理——系统指令与最近轮次必留、中间历史摘要压缩、长文档走检索、大工具结果结构化裁剪；压缩要保留可回溯引用；子代理隔离是另一种解法
**假好**：只做截断（丢最前面）；把所有历史塞进向量库
**追问**：① 压缩会丢什么，怎么补救 → ② 什么时候该开子代理 → ③ 记忆写什么、什么时候失效

### 循环终止与死循环
**触发**：提到"多轮执行""自主规划"
**好回答**：设最大轮次/最大 token/最大时长；检测重复动作（同工具同参数）并打断；把"无法完成"作为合法终止状态；关键步骤人工确认；系统层强制兜底，不能只靠模型自觉
**假好**：只设一个很大的最大轮次
**追问**：① 怎么判断它在绕圈 → ② 终止条件写在哪 → ③ 卡住时用户看到什么

### 长任务状态
**触发**：提到"跑几十分钟的任务""批处理"
**好回答**：状态外部化（进度、已完成步骤、中间产物持久化），支持断点续跑；任务队列异步执行；区分可重入与不可重入步骤（发邮件、下单不可重复执行）；长任务要有进度可见性与人工接管
**假好**：把状态全放在上下文里
**追问**：① 中途挂了怎么续 → ② 哪些步骤不能重跑 → ③ 幂等键怎么设计

### 成本与延迟
**触发**：提到"上线""用户量""成本可控"
**好回答**：模型路由（简单任务走小模型）、精确缓存 + 语义缓存、上下文裁剪、并行工具调用、流式输出、限制最大轮次；先测量再优化，用 trace 找耗时与 token 大头；语义缓存要防相似但答案不同的风险
**假好**：直接换最便宜的模型；不谈瓶颈在哪
**追问**：① P95 延迟多少，瓶颈在哪 → ② 缓存命中率多少 → ③ 换小模型会掉什么能力

## 三、效果与验证

### RAG 失败定位
**触发**：提到"RAG""知识库""检索"
**好回答**：先分召回问题还是排序问题还是生成跑偏。召回：切块按语义/标题层级而非固定字数、混合检索、query 改写与多查询扩展；排序：rerank、元数据过滤；表格/代码/公式要专门处理
**假好**：盲目调大 top_k；只说"接了个向量库"
**追问**：① 检索命中率多少 → ② 答错时是没检索到还是答偏了，怎么区分 → ③ 切块策略为什么这么定

### 评测体系
**触发**：报"准确率 95%""效果很好"
**好回答**：分层评测——组件级（检索命中、工具调用正确率）、任务级（端到端完成率）、体验级（延迟、成本、轮次）；有固定评测集与基线；LLM-as-judge 有位置/长度/自我偏好，需人工抽检校准；难例建回归集
**假好**：只报一个准确率；评测集里混入了调优时用过的样本
**追问**：① 评测集多大，怎么来的 → ② 有没有被污染 → ③ 错的那部分是致命还是可容忍

## 四、落地与贡献

### 上线鸿沟
**触发**：提到"已上线""内部试点"
**好回答**：真实输入的长尾分布（demo 是精选样本）、并发与延迟、成本、权限与数据隔离、错误处理、用户预期管理、无法解释的失败；上线前要做的是建评测集、埋点、灰度、人工兜底，不是加功能
**假好**：认为"再加点 prompt 就能上线"；把演示效果当产品效果
**追问**：① 灰度怎么分的 → ② 用户报错你怎么知道 → ③ 模型不可用时降级到什么

### 个人贡献
**触发**：满篇"我们"，或"参与设计"
**好回答**：说得清自己拍板的那一步（检索策略、tool schema、评测集、路由规则），以及改了几版、为什么改
**假好**：团队成果，个人动作模糊
**追问**：① 哪一步是你定的 → ② 换个人能不能做 → ③ 如果这步错了会怎样
