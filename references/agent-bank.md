# 智能体开发题库（含答案锚点）

按层级分档。`必答` 是命中即得分的最低要求，`加分` 是资深信号，`陷阱` 是高频扣分点。
重点考察工程落地判断力，而非名词背诵。凡回答只堆术语、说不出取舍的，一律不给高分。

---

## L1 · 基础概念（0-3 年）

**A101｜大模型为什么会产生幻觉？工程上怎么缓解？**
- 必答：本质是下一 token 预测在缺乏依据时仍会生成高置信内容；训练目标奖励流畅而非真实。缓解：检索增强、约束输出格式、要求引用来源、降低 temperature、加校验层、对不确定问题允许弃答。
- 加分：幻觉分"事实性幻觉"与"忠实性幻觉"（有依据但答偏），缓解手段不同；加一句提示词治不了根本问题。
- 陷阱：认为"换成更大的模型就没有幻觉"。

**A102｜描述一个完整的 RAG 链路。**
- 必答：文档解析 → 清洗与结构化 → 切块（chunk）→ 向量化 → 入库索引 → 查询改写 → 检索（向量/关键词/混合）→ 重排 → 上下文组装 → 生成 → 引用与后处理。
- 加分：每一环都有失败模式，效果差时要能定位是哪一环（召回不够 vs 排序不对 vs 生成跑偏）；离线要做检索命中率与答案正确率分开评估。
- 陷阱：把 RAG 等同于"接个向量库"。

**A103｜function calling 是怎么实现的？**
- 必答：把工具签名（名称、描述、参数 schema）注入上下文，模型输出结构化的调用意图，由运行时解析、执行、把结果回填给模型，再进入下一轮。
- 加分：模型本身不执行任何东西，可靠性取决于 schema 清晰度与错误信息设计；并行调用、流式下的工具调用、参数校验都是工程要点。
- 陷阱：说"模型会自己去调 API"。

**A104｜哪些问题 prompt 能解决，哪些不能？**
- 能解决：格式约束、角色与语气、任务分解提示、少量示例、输出长度控制。
- 不能解决：知识缺失（需检索或微调）、需要实时数据（需工具）、需要精确计算（需代码执行）、需要严格权限控制（需系统层）。
- 加分：判断标准是"信息是否在上下文里"——不在上下文里的，prompt 再怎么写也变不出来。
- 陷阱：所有问题都先想"怎么写 prompt"。

**A105｜上下文窗口不够用怎么办？**
- 必答：分层处理——保留系统指令与最近轮次、中间历史做摘要压缩、长文档走检索而非全量塞入、大工具结果做结构化裁剪后回填。
- 加分：压缩会丢信息，要保留"可回溯引用"（如摘要里带原始片段 id）；子代理隔离是另一种解法——把脏活放在独立上下文里跑完只回结论。
- 陷阱：只做截断（丢掉最前面的内容）。

**A106｜怎么保证模型稳定输出结构化 JSON？**
- 必答：优先用原生结构化输出/JSON schema 约束，其次用严格格式示例 + 校验重试；解析失败要有兜底（重试、降级到宽松解析、人工介入）。
- 加分：schema 越复杂越容易失败，要拆小；枚举值要给明确列表；对必填字段缺失做专门校验。
- 陷阱：只在 prompt 里写"请输出 JSON"。

**A107｜temperature、top_p 这些参数实际影响什么？**
- 必答：控制采样随机性。结构化抽取、工具调用、代码生成用低温度；创意生成、头脑风暴用高温度。
- 加分：温度不改变模型知识，只改变分布采样；同温度下结果仍可能不同，需要幂等设计时要在系统层做缓存而非指望确定性。
- 陷阱：认为 temperature=0 就一定完全确定。

## L2 · 进阶实战（3-5 年）

**A201｜ReAct、Plan-Execute、Reflection 各自适合什么场景？**
- ReAct：边想边做，适合步骤不确定、需要根据中间结果调整的探索型任务。
- Plan-Execute：先出完整计划再执行，适合步骤可预判、需要并行或需要人审的任务。
- Reflection：生成后自评再改，适合有明确评价标准（如代码可运行、答案可验证）的任务。
- 加分：三者可组合（先 Plan 再 ReAct 执行，关键节点 Reflection）；Reflection 成本高，只在可验证任务上开。
- 陷阱：认为"Reflection 一定提升效果"（无外部信号的自评容易自我强化错误）。

**A202｜什么时候该用多智能体？它的失败模式是什么？**
- 该用：子任务可清晰切分且各自需要不同上下文/工具；需要并行；需要独立视角做交叉验证。
- 不该用：任务本身线性、上下文无法有效传递、协调成本高于收益。
- 失败模式：信息在交接中丢失、职责重叠导致重复劳动、错误在链路中放大、调试困难（不知道哪一环出错）、成本成倍上升。
- 加分：能用单 Agent + 工具 + 结构化状态解决的，优先不上多智能体。
- 陷阱：默认"多智能体更高级"。

**A203｜检索效果差，你会怎么优化？**
- 必答：先定位是召回问题还是排序问题。召回：切块策略（按语义/标题层级而非固定字数）、加关键词检索做混合、query 改写与多查询扩展、补同义词。排序：加 rerank 模型、加元数据过滤（时间/部门/权限）。
- 加分：切块要保留上下文重叠与文档结构；表格、代码、公式要专门处理；用真实问题构建评测集再逐项验证。
- 陷阱：盲目调大 top_k。

**A204｜怎么评测一个 Agent 系统？**
- 必答：分层评测——组件级（检索命中、工具调用正确率）、任务级（端到端完成率）、体验级（延迟、成本、轮次）。要有固定评测集与基线，改动前后对比。
- 加分：LLM-as-judge 存在位置偏差、长度偏好、自我偏好，需人工抽检校准并给 judge 明确评分细则；难例要建回归集防止改动引发倒退。
- 陷阱：只报一个"准确率 95%"。

**A205｜设计工具时最容易犯什么错？**
- 必答：工具描述含糊（模型不知道何时该用）、参数语义不清或过多、错误信息不可自愈（只返回"失败"）、工具粒度太细导致调用链过长。
- 加分：好的错误信息要告诉模型"哪里错了、该怎么改"；工具要幂等、要有超时与重试语义；工具数量过多会显著降低选择准确率，需要分层或路由。
- 陷阱：把内部 API 原样暴露成工具。

**A206｜Agent 的记忆怎么设计？**
- 必答：分短期（当前会话上下文）、长期（跨会话的用户偏好/事实）、工作记忆（任务中间状态）。短期靠窗口管理，长期靠外部存储+检索，工作记忆靠结构化 state。
- 加分：写记忆要有筛选（不是什么都记），否则检索噪音越来越大；记忆要有更新与失效机制（用户偏好会变）。
- 陷阱：把所有对话历史都塞进向量库。

**A207｜怎么降成本和延迟？**
- 必答：模型路由（简单任务走小模型）、缓存（精确缓存+语义缓存）、上下文裁剪、并行工具调用、流式输出改善体感、限制最大轮次。
- 加分：先测量再优化——用 trace 找出耗时与 token 的大头；语义缓存要注意相似但答案不同的风险。
- 陷阱：直接换最便宜的模型。

**A208｜Agent 死循环怎么防？**
- 必答：设最大轮次/最大 token/最大时长；检测重复动作（同样的工具+同样的参数）并打断；把"无法完成"作为合法终止状态；关键步骤加人工确认。
- 加分：终止条件要写进系统提示，同时系统层强制兜底（不能只靠模型自觉）。
- 陷阱：只设一个很大的最大轮次。

**A209｜微调、RAG、prompt 怎么选？**
- prompt：先试，成本最低。
- RAG：知识需要更新、需要溯源、知识量大的场景。
- 微调：需要固定风格/格式、需要压缩成本（用小模型替代大模型）、任务模式稳定但 prompt 表达不清的场景。
- 加分：微调不擅长注入新知识（易幻觉且难更新）；三者常组合——微调定行为，RAG 供知识。
- 陷阱：遇到问题就说"微调一下"。

**A210｜长任务（跑几十分钟）怎么保证不丢状态？**
- 必答：外部化状态（把进度、已完成步骤、中间产物持久化），支持断点续跑；任务队列异步执行；失败重试要幂等。
- 加分：区分可重入与不可重入步骤（发邮件、下单不可重复执行）；长任务要有进度可见性与人工接管入口。
- 陷阱：把状态全放在上下文里。

## L3 · 资深/架构（5 年以上）

**A301｜Agent 上生产的可靠性怎么保证？**
- 必答：边界设计（哪些动作必须人工确认）、幂等与事务（写操作要有唯一键与补偿）、超时与重试（区分可重试错误）、降级（模型不可用时退回规则或人工）、审计（完整 trace 留存）、灰度与回滚。
- 加分：把 Agent 当分布式系统对待——失败是常态；建立 SLO（成功率、P95 延迟）与告警；关键路径要有确定性实现兜底。
- 陷阱：只谈 prompt 优化和模型效果。

**A302｜demo 很惊艳，上线就崩，鸿沟在哪？**
- 必答：真实输入的长尾分布（demo 是精选样本）、并发与延迟、成本、权限与数据隔离、错误处理、用户预期管理、以及无法解释失败原因。
- 加分：上线前要做的不是"再加功能"，而是建评测集、埋点、灰度、以及人工兜底通道。
- 陷阱：认为"再加点 prompt 就能上线"。

**A303｜什么场景不该用 Agent？**
- 必答：结果要求 100% 确定的（账务、清算）、延迟极敏感（毫秒级）、成本极敏感且规则可穷举、责任无法归属的高风险决策、以及输入输出都高度结构化的简单任务。
- 加分：Agent 的价值在"处理开放性"，一旦问题被规则化，回归传统工程更可靠更便宜。
- 陷阱：把 Agent 当万能解。

**A304｜怎么建数据飞轮？**
- 必答：采集真实使用数据（含失败案例）→ 人工标注关键样本 → 进入评测集与训练集 → 迭代 → 再上线验证。关键是失败样本的闭环。
- 加分：要防评测集污染（用过的样本不能再当测试集）；标注规范要稳定，否则数据不可比。
- 陷阱：只收集成功案例。

**A305｜评测集被污染了怎么办？**
- 必答：重建 holdout 集（严格隔离，不参与任何调优）、用新时间段数据、做对抗性难例集、以及监控"分数突然暴涨"这种异常信号。
- 加分：模型厂商训练数据不可控，公开基准只能作参考，必须建自己的私有评测集。
- 陷阱：继续用公开榜单证明效果。

**A306｜多轮对话里指令漂移怎么处理？**
- 必答：系统指令在每轮重注入或放末尾强化、关键约束做运行时校验（不靠模型记性）、状态显式化（把当前约束写进 state）、定期总结重述。
- 加分：长会话要主动做"约束回读"；对不可违背的规则要在系统层拦截而非提示层。
- 陷阱：认为"写在 system prompt 里模型就会一直遵守"。

## 陷阱题 / 压力题

**A401｜"加个 Agent 就能解决这个问题"——你同意吗？**
- 要点：先问问题是否真的开放。若可用确定性流程解决，Agent 带来的是不确定性、成本与调试难度。判断标准：输入是否高度多样、步骤是否需要动态决策、失败是否可容忍。
- 扣分：无条件附和。

**A402｜效果不好，换个更大的模型不就行了？**
- 要点：先定位瓶颈——是检索没给到信息、工具用错、还是生成跑偏。模型能力只解决其中一类。盲目换模型会同时放大成本与延迟。
- 扣分：认可"换模型是首选方案"。

**A403｜我们的 Agent 准确率 95%，可以上线了吧？**
- 要点：追问——95% 是在什么分布上测的？5% 的错误是什么类型（致命/可容忍）？错误是否可被用户发现和纠正？成本和延迟多少？上线后如何监控？
- 扣分：认可"95% 够了"。
